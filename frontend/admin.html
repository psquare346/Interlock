Format guide — required fields, special characters, decimals
columnreq?rules
supplier_part_idrequiredMax 35 chars (SAP limit). Letters, digits, dash, underscore, period, slash. Avoid commas, semicolons and quotes — they fight the CSV format. Must be unique within the file. A row without one is always sent to manual review; the system never invents part numbers.
descriptionrequiredMax 40 chars land in SAP's short text; anything longer is kept but spills to long_description automatically. Accents/umlauts are fine (file should be UTF-8). Avoid line breaks inside a cell.
uomrequiredBest: SAP codes EA, PAK, KAR, KG, G, L, ML, M, MM, CM, ROL, PAA, DZ, SET, BT, TU, KI. Common synonyms are auto-normalized (pcs, each, ST, Stk → EA; box, carton → KAR; pair → PAA…). Unknown units stop the row for review.
unit_pricerequiredPositive number, up to 4 decimal places (e.g. 0.4275). Both 1,234.56 and 1.234,56 styles parse. Currency symbols are tolerated but leave them out. Zero or negative fails the row.
currencyrequired3-letter ISO code (USD, EUR, GBP…). One currency per file is best practice.
price_unitoptionalWhole number ≥ 1, default 1. "Price is per this many units": price 42.00 with price_unit 100 = 0.42 each. Getting this wrong is the classic 100× purchasing error — when in doubt, use 1 and price per single unit.
unspscoptional8 or 10 digits, no dots. If missing, classification queues for review (or the AI proposes one when a key is configured).
material_groupoptionalYour SAP material group. Never auto-approved — it drives GL account determination, so a human always confirms it.
manufacturer / manufacturer_part_idoptionalFree text / same character rules as supplier_part_id.
lead_time_daysoptionalWhole number ≥ 0.
long_descriptionoptionalFree text, no practical limit.

Result

Review queue

The human gate. Each queued row explains why it's here. You can approve, reject, or edit a row — an edit is re-validated by the same hard rules and still needs your approve click. Confirm mapping saves this file's column mapping to the supplier so the next load is zero-touch.

Publish

Publishing releases the version to the punchout storefront and supersedes the previous published version. The API refuses while any row is still undecided — clear the queue first. Rejected rows simply don't ship.

Versions

Pricing

Quantity-break ladders load against a contract and are validated as a whole (no gaps, no overlaps, exactly one open-ended top tier, price must fall as quantity rises). Resolution is pure arithmetic — watch price_unit: 35.00 with price_unit 100 means 35 dollars per hundred.

How tiers work — one line per tier

3 tiers = 3 lines, grouped by repeating the same supplier_part_id. There is no "tier 1 / tier 2" label column — the quantity range on each line IS the tier, which removes any chance of labels and ranges disagreeing:

supplier_part_id,min_qty,max_qty,unit_price,price_unit,currency ACME-1001,1,9,0.4200,1,USD ← tier 1: qty 1–9 ACME-1001,10,49,0.3800,1,USD ← tier 2: qty 10–49 ACME-1001,50,,0.3500,1,USD ← tier 3: qty 50+ (max_qty EMPTY = no upper limit)

Rules enforced on upload — the whole ladder is rejected with the exact reason if any fail:

  • First tier must start at min_qty 1
  • No gaps, no overlaps: each tier's max_qty + 1 = next tier's min_qty (…9 → 10…, …49 → 50…)
  • Exactly one open-ended top tier (empty max_qty), and it must be the highest
  • Price must fall (or stay equal) as quantity rises — a rising ladder is almost always a data error
  • Prices: positive, up to 4 decimals; one currency per ladder, matching the contract currency
  • Validity dates must fit inside the contract window

Line order in the file doesn't matter — tiers are sorted by min_qty. A part with no tiers simply uses its catalog list price.

Policy

Rules are deterministic code — no model in the request path. Uploads land in draft; activation clamps the window to the bound contract and supersedes overlapping versions. Try the scenarios: every fired rule is shown, and the most severe action wins.

Users & privileges

Admin only. Every account holds exactly the privileges you check here — approve needs catalog_review, releasing a version needs catalog_publish, and so on. The admin role implies everything. You can't remove the last active admin — the tenant would lock itself out.
